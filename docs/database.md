## Setup

```bash
cd backend
cp .env.example .env        # then set DATABASE_URL
npm install
npm run db:migrate          # applies all migrations (prisma migrate deploy)
```

## Conventions

- PostgreSQL table and column names are `snake_case`; Prisma model and field names are `camelCase`.
- Primary keys are UUIDs generated by PostgreSQL.
- All timestamps are `timestamptz` (stored in UTC, displayed in Africa/Mogadishu time).
- Foreign keys use `ON DELETE RESTRICT`, so history rows are never removed by cascade. The one exception is `exam_rule_topics`, which is deleted with its rule; a rule already used by an attempt cannot be deleted, because `attempt_questions` references it.
- Money and marks use `DECIMAL`, never floating point.

## Raw SQL objects

Prisma cannot express CHECK constraints, triggers or partial unique indexes, so these are written by hand at the end of the init migration. `prisma migrate diff` reports no drift with them in place, so later migrations will not try to remove them.

Trigger errors use SQLSTATE `P0001`, and the error message is a stable code (for example `ATTEMPT_DEADLINE_PASSED`). The backend maps each code to a translated Somali/English message.

### Payment outcomes (simulated)

| Outcome | How it happens | Database guarantees |
|---|---|---|
| SUCCESS | Correct demo PIN, checked by the backend | Only from PENDING_PIN, after Yes, before expiry, with fewer than 3 wrong attempts and a valid DEMO receipt. The PIN counter doesn't change. |
| FAILED | Third wrong demo PIN | Only from PENDING_PIN, in the same update that records the 3rd attempt |
| CANCELLED | Student presses No, or cancels during PIN entry | From PENDING_CONFIRMATION or PENDING_PIN, before expiry. The PIN counter doesn't change. |
| EXPIRED | 5 minutes after creation | Only once `expires_at` is reached. After that, nothing else is allowed. |

All four outcomes are final. The 5-minute expiry is fixed in the database, and there is no `.env` setting for it.

The database can't check the demo PIN itself, because the PIN is never stored. The backend compares it with `DEMO_PAYMENT_PIN` using `crypto.timingSafeEqual`, then records SUCCESS or a wrong attempt. The database guarantees that SUCCESS can only be recorded at the right point in the flow.

## Rules left to the service layer

These rules span several rows or tables, so the service layer enforces them. Each will be covered by automated tests:

- **Questions:** multiple choice has 4–5 options with exactly one correct, and True/False has exactly 2. Rubric marks add up to the question's marks.
- **Exam rules:** there are enough eligible questions across all rules together (no question used twice).
- **Schedules:** no overlapping approved exams for any shared student.
- **Access:** students must be enrolled, and can start only inside the window, from an allowed room or network, and after paying if the exam has a fee.
- **Ownership:** every request checks that the attempt or payment belongs to the current user. A failed check returns 404.
- **Grading:** blind second grading and the 20% discrepancy rule.
- **Payments:** checking the demo PIN itself, and marking unfinished payments EXPIRED once the database allows it.

## Known limits of the database protections

- `TRUNCATE` and dropping the schema bypass the row triggers. They are only used in test resets (`prisma migrate reset`).
- `sms_outbox_no_secrets_chk` checks the top-level keys of `params` only. Keeping passwords out of the message `body` is enforced by the message templates and by tests.
