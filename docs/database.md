# Database

PostgreSQL 15 or newer. Development and testing use PostgreSQL 17. The schema is managed with Prisma 7.10.1.

Version 15 is the minimum because, from version 15, ordinary roles can't create objects in the `public` schema by default. The access-security rules rely on that: `exam_app` must not be able to create tables or functions.

## Setup

```bash
cd backend
cp .env.example .env        # set MIGRATE_DATABASE_URL (owner); see .env.example for formats
npm install
npx prisma migrate status   # read-only: which migrations are not applied yet
npm run db:migrate          # applies all migrations (prisma migrate deploy) as the owner
npm run db:app-password     # enables exam_app login and writes DATABASE_URL into .env
npm run db:seed:demo        # optional demo data (docs/demo-data.md)
npm run db:check            # read-only health check: every line must say PASS
```

| Script | What it does |
|---|---|
| `db:supabase-login` | Asks for the Supabase password (hidden typing) and writes `MIGRATE_DATABASE_URL` |
| `db:migrate` | `prisma migrate deploy`: the only migration command for Supabase and campus databases |
| `db:migrate:dev` | Creates a new migration. **Local PostgreSQL only**; it refuses any other host. |
| `db:app-password` | New random `exam_app` password, sent to the server only as a SCRAM-SHA-256 hash; writes `DATABASE_URL` |
| `db:seed:demo` | Demo data as `exam_app`. One transaction, refuses to run twice, never deletes. |
| `db:check` | Read-only structure, security and data-integrity checks |
| `verify:db` | Test suite in non-destructive verification mode against the configured database |
| `db:generate` / `db:validate` | Prisma Client generation and schema validation (no database needed) |

The one-time setup is described in [database-environments.md](database-environments.md): local roles in [Local PostgreSQL 17 setup](database-environments.md#local-postgresql-17-setup), and Supabase in [Supabase setup](database-environments.md#supabase-setup-hosted-environment).

**TLS:** Supabase connections verify the server against Supabase's root CA, `backend/certs/supabase-ca-2021.crt`.

Every rule below is covered by the automated tests. See [testing.md](testing.md).

## Conventions

- PostgreSQL table and column names are `snake_case`; Prisma model and field names are `camelCase`.
- Primary keys are UUIDs generated by PostgreSQL.
- All timestamps are `timestamptz` (stored in UTC, displayed in Africa/Mogadishu time).
- Foreign keys use `ON DELETE RESTRICT`, so history rows are never removed by cascade. The one exception is `exam_rule_topics`, which is deleted with its rule; a rule already used by an attempt cannot be deleted, because `attempt_questions` references it.
- Money and marks use `DECIMAL`, never floating point.

## Raw SQL objects

Prisma cannot express CHECK constraints, triggers or partial unique indexes, so these are written by hand at the end of the init migration. `prisma migrate diff` reports no drift with them in place, so later migrations will not try to remove them.

Trigger errors use SQLSTATE `P0001`, and the error message is a stable code (for example `ATTEMPT_DEADLINE_PASSED`). The backend maps each code to a translated Somali/English message.

### Payment outcomes (simulated)

| Outcome | How it happens | Database guarantees |
|---|---|---|
| SUCCESS | Correct demo PIN, checked by the backend | Only from PENDING_PIN, after Yes, before expiry, with fewer than 3 wrong attempts and a valid DEMO receipt. The PIN counter doesn't change. |
| FAILED | Third wrong demo PIN | Only from PENDING_PIN, in the same update that records the 3rd attempt |
| CANCELLED | Student presses No, or cancels during PIN entry | From PENDING_CONFIRMATION or PENDING_PIN, before expiry. The PIN counter doesn't change. |
| EXPIRED | 5 minutes after creation | Only once `expires_at` is reached. After that, nothing else is allowed. |

All four outcomes are final. The 5-minute expiry is fixed in the database, and there is no `.env` setting for it.

The database can't check the demo PIN itself, because the PIN is never stored. The backend compares it with `DEMO_PAYMENT_PIN` using `crypto.timingSafeEqual`, then records SUCCESS or a wrong attempt. The database guarantees that SUCCESS can only be recorded at the right point in the flow.

## Access security

Added by migration `20261103150000_database_access_security`.

### Roles

| Role | Used by | Can do |
|---|---|---|
| Owner (`exam_owner` locally, `postgres` on Supabase) | Prisma CLI only, through `MIGRATE_DATABASE_URL` | Owns every table, type, function and trigger, and applies migrations. Never used by the running application. |
| `exam_app` | The Express application, through `DATABASE_URL` | See the privileges below. Not a superuser, can't skip RLS, can't create roles or databases, owns nothing. |
| `anon`, `authenticated`, `service_role` (Supabase only) | Nobody | Nothing: all privileges on our tables, sequences and functions are removed, including privileges Supabase would grant to future objects |

The migration creates `exam_app` without a password. Each environment enables login separately (`ALTER ROLE exam_app WITH LOGIN PASSWORD '...'`), so no password is ever stored in git.

### exam_app privileges

| Tables | Privileges |
|---|---|
| All 36 tables | SELECT, INSERT, UPDATE |
| `audit_logs`, `grade_revisions`, `result_publications` | SELECT, INSERT only (the append-only triggers also block changes) |
| `question_options`, `accepted_answers`, `rubric_criteria`, `exam_rules`, `exam_rule_topics`, `schedule_rooms`, `schedule_invigilators`, `grading_scale` | Also DELETE, for editing drafts. Locked versions and used rules stay protected by the triggers and foreign keys. |
| `_prisma_migrations` | None |

`exam_app` has no TRUNCATE, REFERENCES or TRIGGER privilege and owns no objects. It therefore **cannot switch off triggers, drop constraints or alter tables**, so the database rules hold even if the application had a bug or an SQL injection.

### Row-level security

- RLS is enabled on all 36 tables and on `_prisma_migrations`. The migration fails if any table in `public` is left without RLS.
- Each of the 36 tables has exactly one policy, `<table>_exam_app_access`, applying **only to `exam_app`**, with `USING (true) WITH CHECK (true)`.
- There is no policy for `PUBLIC`, `anon`, `authenticated` or `service_role`. A role without a policy sees no rows, even if it has been granted table privileges.
- The owner is not restricted by RLS, so migrations and the Prisma CLI work as before.

### Student-level authorization lives in Express

The `exam_app` policy lets the application see **all rows**. The database can't tell which student, lecturer or invigilator is using the application. Every per-user rule is therefore enforced by the Express service layer, on every request, for example:

- a student reads and changes only their own attempt, answers, payments and published results (a failed ownership check returns 404);
- a lecturer works only with their own courses' question banks, exams and grading;
- an invigilator sees only the sessions assigned to them;
- correct answers are hidden until results are published and review is allowed.

These rules will get their own automated tests when the backend is built. RLS here is a safety layer against outside access, not the application's permission system.

## Rules left to the service layer

These rules span several rows or tables, so the service layer enforces them. Each will be covered by automated tests:

- **Questions:** multiple choice has 4–5 options with exactly one correct, and True/False has exactly 2. Rubric marks add up to the question's marks.
- **Exam rules:** there are enough eligible questions across all rules together (no question used twice).
- **Schedules:** no overlapping approved exams for any shared student.
- **Access:** students must be enrolled, and can start only inside the window, from any device or network, and after paying if the exam has a fee.
- **Ownership:** every request checks that the attempt or payment belongs to the current user. A failed check returns 404.
- **Grading:** blind second grading and the 20% discrepancy rule.
- **Payments:** checking the demo PIN itself, and marking unfinished payments EXPIRED once the database allows it.

## Known limits of the database protections

- `TRUNCATE` and dropping tables bypass the row triggers. Only the owner can do either; `exam_app` can't. The test run's reset drops the application's tables, but only in a dedicated test database.
- `sms_outbox_no_secrets_chk` checks the top-level keys of `params` only. Keeping passwords out of the message `body` is enforced by the message templates and by tests.
